# Vibe Coding 统一题库

## 高频问题（口语标准答法）

## 1. 你怎么定义 vibe coding？
我把 vibe coding 定义为一种人机协同的工程范式，不是“让 AI 自动写代码”，而是“让 AI 放大工程师产能”。
在这个范式里，AI 主要负责需求拆解、方案探索和代码草稿，人负责问题定义、架构边界、风险控制和最终决策。
它的核心不在于生成速度，而在于能不能通过类型检查、测试、代码评审和安全合规形成可验证闭环。
所以我会说，vibe coding 的本质是：AI 负责提速，人类对正确性和可维护性负责到底。

## 2. 你怎么把模糊需求转成可执行 prompt（不是一句泛泛要求，而是 AI 拿到后可以直接按步骤产出可验证结果的指令）？
我一般用 5 步把模糊需求转成可执行 prompt：
1. 先做需求收敛：先明确业务目标、关键约束和成功标准，避免 AI 在错误方向高质量输出；
2. 再做任务切片：把大需求拆成可独立验证的小任务，比如“先方案、再实现、再测试、再优化”；
3. 使用四段模板：业务背景、工程约束、输入输出、验收标准，把自然语言需求转成工程任务；
4. 先要计划再要代码：复杂任务先让 AI 产出实现计划或伪代码，我确认路径正确后再生成代码；
5. 做双重验证：机器侧过 type check、lint、测试，人工侧审查架构一致性和风险点。

举个例子，我不会只说“帮我优化性能”，而会明确：目标是降低渲染耗时；约束是不改对外接口；输入是指定模块代码；输出是改动方案和原因；验收是 lint/typecheck 全过、关键交互无回归、性能指标下降。

本质上，可执行 prompt 不是“把问题丢给 AI”，而是把模糊需求转成有边界、有步骤、有验收的可验证任务。

## 3. 你如何判断 AI 生成代码是否可信？
我通常用“三层校验 + 双重验证”判断 AI 代码是否可信：
1. 需求正确性：先看主流程是否满足业务目标，是否漏掉关键场景；
2. 工程可靠性：再看边界条件、异常处理、类型安全和性能影响；
3. 可维护性：最后看可测试性、可读性、可扩展性，以及是否符合团队规范。

三层通过后，我会再做双重验证：
1. 机器验证：type check、lint、单测、关键路径回归；
2. 人工验证：架构一致性、安全风险和业务语义是否正确。

比如 AI 改了一个数据聚合函数，我不会只看“能跑”，而会补边界测试（空数据、异常值、超大数据量），同时确认复杂度没有恶化、返回结构不破坏下游依赖，再决定是否合并。

本质上，可信不是“看起来对”，而是“经过验证后仍然成立”。

## 4. 怎么避免 AI 代码“能跑但不可维护”？
我会从源头做约束，而不是事后补救。具体做法是先定义模块职责、命名规范、类型边界和接口契约，再让 AI 在边界内实现。
同时要求 AI 输出“为什么这样设计”的说明，避免只给代码不讲取舍。
最后用测试和 review 检查是否引入隐性耦合，确保代码不仅能跑，而且能被团队长期维护。

## 5. AI 生成后你第一步做什么？
第一步不是看页面，而是先验证。通常我会先跑现有测试，再补关键路径测试，确认没有回归。
如果是新功能，我会先写最小验收用例再接 AI 代码，确保“定义完成”是可执行的。
因为视觉效果容易误导，测试结果才是最可靠的质量信号。

## 6. 你如何做质量门禁？
我把质量门禁做成固定流水线，而不是靠自觉。基础门禁是 type check、lint、单测、关键路径回归。
对高风险改动还会加性能基线和安全检查，比如依赖漏洞、权限校验、输入校验。
规则很简单：任何门禁不过都不合并，AI 代码和人工代码同标准。

## 7. 你如何处理 AI 幻觉？
我处理 AI 幻觉的原则是“先质疑、后采纳”。具体会做三件事：要求给依据、用最小样例复现、用测试验证结论。
如果 AI 给的是黑盒建议，我会让它先解释推理链路和边界条件，再决定是否采用。
只有可复现、可验证、可解释的建议才会进入代码库。

## 8. 你如何做安全和合规控制？
我把安全和合规当硬约束，不会因为提效放松。首先不把敏感数据直接放入 prompt，必要时做脱敏或最小化上下文。
其次对依赖做漏洞和许可证检查，避免引入供应链风险。
最后对认证、权限、输入校验、日志脱敏等高风险点做人工复核，确保可上线而不是只可演示。

## 9. 你如何让 AI 输出符合团队规范？
我会把团队规范前置成“可执行约束”，而不是写在 wiki 里等人记忆。
比如固定代码模板、目录约定、提交规范、PR 清单，并把这些规则放进 lint、CI 和 review checklist。
这样 AI 输出天然贴近团队标准，review 关注点可以从格式问题转向设计和业务价值。

## 10. 你如何衡量 AI 是否真的提效？
我会看三组核心指标：交付周期、缺陷率、返工率，再加一个稳定性指标（上线后回滚或事故次数）。
如果开发阶段看起来变快，但返工和线上问题变多，我会把它判定为伪提效。
真正的提效是“总成本下降”，不是“写代码更快”。

## 11. 什么时候你会明确不用 AI？
涉及核心安全逻辑、权限模型、关键算法、高风险重构时，我会以人工设计为主，AI 只做参考。
这些场景错误代价高，不能把主导权交给概率模型。
我的原则是：风险越高，人类决策权越高。

## 12. 讲一个你实践 vibe coding 的案例
在 AI 灾害分析项目里，我把 AI 用在高重复、低风险环节，比如节点模板、测试样例和文档初稿。
人主要负责高价值决策，包括流程编排、状态契约、异常策略和上线标准。
这种分工让我们在保证质量的前提下加快了交付，执行引擎更快落地，并沉淀成对内可复用的 SaaS API 能力。

## 13. 你未来做 AI coding 工具，优先解决什么痛点？
我会优先解决“从需求到上线”的最后一公里，因为这段最耗时也最容易失控。
目标是把需求拆解、代码生成、测试校验、质量门禁串成可观测、可审计、可回滚的标准化流水线。
这样团队得到的不是一次性提速，而是长期稳定的工程生产力。

## 14. 关于 vibe coding，你用过什么工具？
我实践 vibe coding 主要用四类工具，并且会区分“开发入口”和“底层模型能力”。
1. 生成类：我以 GitHub Copilot 作为 IDE 内的统一入口，同时配合 ChatGPT、Claude、Codex 做需求拆解、方案对比、代码草稿和多文件重构；
2. 编排类：LangChain、LangGraph、Ollama、OpenAI API，用于多步骤任务编排、状态流转和模型切换；
3. 质量类：TypeScript、ESLint、单元测试和关键路径回归测试，确保 AI 产出可验证；
4. 协作类：GitHub PR、Code Review、Prompt 模板沉淀，保证团队可复用和可维护。

一句话总结：我会用 Codex 和 Copilot 提升开发速度，但不会把任何模型当决策者，最终必须通过工程门禁和人工评审再合入。

## 15. Python FastAPI 是什么？
FastAPI 是一个用于构建后端 API 的 Python 框架，可以理解为“高性能 + 类型驱动 + 自动文档”的后端开发方案。
它的核心特点有四个：
1. 自动参数校验：基于类型注解自动校验请求参数，减少手写校验代码；
2. 自动 API 文档：默认生成 OpenAPI / Swagger 文档，便于前后端联调；
3. 异步支持好：适合 I/O 密集型服务场景，接口并发能力更好；
4. 开发效率高：代码简洁、规范统一，适合快速交付可维护的 API。

面试一句话版：FastAPI 是 Python 生态里一个高性能、类型驱动、自动文档化的 API 框架，适合快速构建可维护的后端服务。

## 16. 你这个项目流式 SSE 对话怎么实现的？（备注）
这个项目的流式对话采用“前端手写 SSE 解析”方案，不依赖 EventSource。
实现流程是：
1. 前端发起流式请求：请求体设置 `stream: true`；
2. 读取响应流：通过 `resp.body?.getReader()` 持续 `read()` 分片；
3. 手写 SSE 解析：`TextDecoder` 增量解码后按换行切分，仅处理 `data: ` 开头行，跳过 `data: [DONE]`；
4. 增量渲染 UI：从 JSON 中提取 `choices[0].delta.content`，实时 `onChunk` 输出，形成逐字打印效果。

补充：本项目有两条路径，直连模型时是真 SSE 流式解析；走 ai-flow 工作流时是“先返回完整文本，再前端模拟打字机流”。

## 场景模拟题（高概率）
1. 给你一个线上性能问题，你如何用 AI 辅助定位和修复？
我的做法是先人工定义问题边界，再让 AI 提速分析。先用监控和日志确认是 CPU、I/O 还是渲染瓶颈，再把关键指标和代码片段喂给 AI，让它给出 2-3 个可验证假设。接着我按“低风险、可回滚”原则逐个实验，最终用压测和线上指标对比验证效果，确保不是体感优化。

2. 给你一段遗留代码，现场让 AI 重构，你如何控制风险？
我会先锁行为，再做重构。先补最小回归测试和关键快照，保证旧逻辑被覆盖；再让 AI 做小步重构，不做一次性大改；每一步都跑测试和静态检查。这样即使 AI 给出不理想改法，也能快速回退，不会把风险扩散到整段遗留代码。

3. 在 30 分钟内做可演示功能，你如何分工“AI 做什么、人做什么”？
我会把时间拆成三段：前 5 分钟人来定范围和验收标准；中间 20 分钟 AI 生成脚手架、样板代码和基础测试，我负责关键业务逻辑、状态流转和异常处理；最后 5 分钟人来做联调和演示脚本。AI 负责速度，人负责正确性和可讲述性。

4. AI 给出和你经验冲突的方案，你如何做技术决策？
我不会靠感觉拍板，会做证据驱动决策。先把冲突点转成可验证指标，比如性能、复杂度、可维护性和安全风险；让 AI 和人工方案都跑同一套验证用例；最后按团队约束和业务目标做取舍。如果两者都不理想，我会选最稳妥可演进的中间方案。

## Token 相关高频追问（6 问 6 答）

### 1. 你怎么控制 token 成本？
我会把 token 当成工程资源管理，和 CPU、内存一样要做预算。通常从三层控制：
1. 上下文层：系统规则固定，历史对话做摘要，只保留当前任务必要上下文；
2. 任务层：把大任务拆小，按步骤调用，避免一次请求塞太多无关信息；
3. 模型层：按任务难度分级，默认轻模型，只有复杂推理再升级。
我还会给不同场景设预算阈值，比如普通问答优先低成本模式，关键分析任务优先质量模式。目标不是绝对省 token，而是单位 token 产出最大化。

### 2. 长对话里你怎么做上下文管理？
我会做“分层记忆”，避免历史越长越贵、越长越乱：
1. 近期窗口：最近几轮保留原文，保证当前语义完整；
2. 历史摘要：更早内容压缩成结构化摘要，按“目标、约束、已决策事项、待办”保存；
3. 关键事实库：接口约束、术语定义、不可变规则单独存放，按需检索注入。
这样既能维持连续性，也能避免把无关历史反复付费注入。

### 3. prompt 太长导致慢和贵，你怎么处理？
我通常按“压缩、切分、检索”三步处理：
1. 压缩：删除无关描述、合并重复约束、把整段日志改成关键片段和错误摘要；
2. 切分：把一个大 prompt 改成多轮小任务，先生成计划，再逐步实现和校验；
3. 检索：需要引用知识时改为按需检索注入，而不是把全量文档放进上下文。
举个例子，排查报错时我不会贴全部日志，而是先给错误栈、触发条件和相关代码片段，速度和准确率都会更好。

### 4. 你怎么平衡 token 成本和回答质量？
我会先做任务分级，再做策略匹配：
1. 高风险任务（架构决策、安全逻辑、核心算法）优先质量，允许更高 token；
2. 中风险任务（重构建议、测试补齐）做平衡模式；
3. 低风险任务（文档润色、模板生成）优先低成本。
运行时会监控 token、延迟和通过率，超过预算就触发降级策略，比如摘要模式、轻模型或分步执行。我的原则是“先达标，再省钱”。

### 5. 你如何评估一次 AI 流程是否划算？
我会用“成本-质量-效率”三维评估，而不是只看 token。
核心指标包括：单任务 token 成本、端到端时延、一次通过率、返工率、线上回滚率。
判断是否划算看总交付成本：如果 token 降了但返工和故障增加，就是伪优化；如果 token 略升但一次通过率明显提高，整体反而更划算。
所以我会看全链路结果，而不是单点指标。

### 6. 你会做哪些 token 级别的工程优化？
我会做四类可落地优化：
1. Prompt 标准化：沉淀任务模板，减少重复描述和无效上下文；
2. 上下文去重：历史消息压缩、重复约束合并、无关信息过滤；
3. 结果缓存：固定规则、通用解释、稳定中间结果缓存复用，减少重复调用；
4. 调用编排：将单次大调用改为多次小调用，必要时并行低成本步骤。
这些优化的共同目标是降低 token 消耗、缩短延迟，并提升输出稳定性。

### Token 题一句话总结
我对 token 的策略是：按任务价值分配上下文和模型能力，用可观测指标管理成本，在质量达标前提下做最小化消耗。

# 90 秒后高概率追问：10 问 10 答（结合项目与简历数据）

## 1. WebGL 项目里，你说“性能明显下降”，具体指标是多少？
当时原方案主要靠 DOM Marker 渲染，点位量上来后主线程会频繁 Layout 和 Repaint。我们压测时在高密度场景帧率大概只有 5fps，交互上会出现明显拖拽掉帧和缩放卡顿。重构后稳定在 55fps+，这是我在项目里最核心的性能收益之一。

## 2. 你做的三件事里，哪一项贡献最大？为什么？
贡献最大的是把渲染路径从 DOM 切到 WebGL，并配合 LOD 分层策略。这个改动本质上是架构级变化，直接把瓶颈从浏览器布局绘制转移到 GPU 批量渲染。后面的 GeoJSON 增量更新和 Worker 拆分是在这个基础上继续压缩刷新延迟和主线程阻塞。

## 3. 这个优化有没有副作用，比如复杂度上升、维护成本增加？
有，主要是工程复杂度上升，比如图层管理、调试成本和团队上手门槛都会增加。我的处理方式是把渲染层、数据层、线程层拆开，并统一接口和类型约束，再配套组件边界和文档，保证复杂度可控。换句话说，我接受必要复杂度，但避免无序复杂度。

## 4. 你在这个项目里是主导还是协作？你个人负责到什么深度？
我是从 0 到 1 主导重构的人，覆盖方案设计、核心实现和落地验证。包括渲染分层策略、GeoJSON Source 增量更新、Worker 数据预处理、以及性能压测和效果验收。最终结果是帧率从 5fps 提升到 55fps+，地图刷新卡顿从 800ms 降到 20ms。

## 5. AI 工作流引擎为什么不用现成方案，为什么要自研？
核心原因是业务要可控、可扩展、可私有化。我们场景里既要支持多步骤条件分支，又要支持本地 Ollama 和云端模型切换，还要和现有业务 API、权限体系、数据上下文深度耦合。现成方案能做 demo，但在多团队复用、权限治理和二次扩展上不够贴合，所以我选择了自研执行引擎。

## 6. 多分支流程下你怎么保证状态一致性？
我做了两件关键事：第一是明确状态结构和节点输入输出边界，第二是通过条件边和执行顺序约束状态流转，避免分支互相污染。简单说就是先定义状态契约，再做流程编排，这样上下文在多轮和多分支下都能保持一致。

## 7. 你说对内 SaaS API 复用，复用了多少团队/场景？
我们把能力抽成 SaaS API，对接方按统一接口接入，不需要重复造轮子。实际效果是灾害分析流水线新增成本从天级降到分钟级，开发同学更关注业务逻辑而不是底层编排细节。这一点在团队协作效率上提升很明显。

## 8. vibe coding 在你项目中具体怎么用，不是口号？
我把它当工程提效工具，不是替代决策。实操上我主要让 AI 加速节点模板、测试样例、文档和重复代码骨架，然后由我做架构边界、关键逻辑和上线质量把关。这样既有速度，也能保证可维护性。

## 9. AI 生成代码如何做质量门禁和安全合规？
我会把 type check、lint、单测和关键路径回归作为固定门禁，不通过就不合入。安全上避免敏感数据进入 prompt，同时做依赖和权限校验，尤其是认证、输入校验和异常处理这些高风险点必须人工复核。结果上我们 AI 助手 API 调用成功率做到 99%+，首字响应小于 1 秒。

## 10. 你未来做 AI coding 工具，最先想解决哪个痛点？
我最先解决的是从需求到可上线代码之间的“最后一公里”，也就是把需求拆解、代码生成、测试校验、质量门禁串成一条标准化链路。因为真正决定团队效率的不是生成一段代码，而是能不能稳定交付。这个方向也和我现在的实践最连续。
