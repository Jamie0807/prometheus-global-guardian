## 项目重难点：

1. 地图渲染引擎重构：从 DOM Marker 到 WebGL GPU 实例化

**一句话总结**：我在最近的项目中从 0 到 1 主导了基于webgl的渲染器引擎的整体重构，将帧率从 5fps 提升至稳定 55fps+，支撑了 10w+ 地理点位的实时流畅渲染。

**背景**：项目初期采用 Mapbox 原生 DOM Marker 方案渲染灾害点位，每个点位对应一个独立 DOM 节点。当数据量超过 1000 个时，浏览器频繁触发 Layout 和 Repaint，帧率急剧跌至 5fps 以下，地图几乎无法交互，这是典型的 DOM 渲染在大数据量场景下的性能天花板，必须从架构层面彻底替换渲染方案。

**核心技术难点**：

- **DOM → WebGL 渲染层迁移**：原有组件逻辑与 DOM Marker 深度耦合，需在不破坏上层业务的前提下整体切换为 WebGL Custom Layer。将点位数据编码为 `Float32Array` 顶点缓冲区，通过顶点着色器和片元着色器完成样式渲染，彻底脱离 DOM 操作。

- **GPU 实例化 + 动态增删的矛盾**：使用 `ANGLE_instanced_arrays` 实现 GPU 实例化，10w+ 点位只需一次 Draw Call。但实时数据推送导致点位频繁增删，每次全量重建 VBO 开销过大——最终采用预分配固定大小缓冲区 + 脏标记（dirty flag）局部更新策略解决。

- **LOD 三级调度 + 视口裁剪**：基于地图缩放层级实现三级 LOD：低缩放级别只渲染聚合簇中心点，中缩放级别渲染区域代表点，高缩放级别才渲染全量点位；结合视口包围盒裁剪，只向 GPU 提交可见区域数据，显存占用降低 60%+。

- **Web Worker 异步数据清洗**：将坐标缺失修复、格式标准化、WGS84 → 墨卡托坐标转换全部移入 Worker，主线程只接收处理完毕的 `Float32Array`，消除数据处理引起的主线程阻塞掉帧。

**结果**：帧率从 5fps 提升至稳定 55fps+，显存占用降低 60%+，10w+ 点位下地图交互流畅无卡顿。

2. 自研 AI 工作流引擎平台：

**背景**：随着公司越来越多的业务需要接入 AI 能力，每个项目都在重复实现 LLM 调用、提示词管理、工具调用等逻辑，研发成本高、复用性差。为此，我主导从零孵化了一个内部 AI 工作流引擎平台，让业务团队通过低代码可视化画布快速编排 AI 流程，无需每次从头集成。

**核心技术难点**：

- **DAG 执行引擎的架构设计**：需要统一调度 LLM 推理、RAG 知识库检索、HTTP 请求、条件分支等完全异构的节点类型。难点在于如何抽象统一的节点接口（NodeExecutor 注册表模式），以及如何实现节点间的数据流转——最终通过 `{{nodeId.output}}` 变量插值机制，在运行时动态解析上游节点输出并注入下游节点入参，保证 DAG 拓扑有序执行。

- **LangGraph 有状态工作流的状态一致性**：LangGraph `StateGraph` 在多分支场景下，节点间状态的合并与覆盖容易出现上下文丢失或污染问题。通过定义严格的 `Annotation.Root` 状态结构与边条件函数，确保多轮对话历史和条件分支下的状态始终一致。

- **本地与云端模型的统一接入**：Ollama 本地模型（Llama3、Qwen）与 OpenAI API 存在接口差异，设计了统一的模型适配层，支持流式与非流式两种输出模式，实现了模型来源对上层业务完全透明。

**结果**：平台以 SaaS API 方式对内开放，在全球灾害监控平台等项目中完成接入，API 调用成功率 99%+，首字响应低于 1 秒，显著降低了各业务线的 AI 集成成本。

**补充：fps 释义**

fps 是“frames per second”的缩写，中文一般称为“每秒帧数”或“帧率”，用于衡量动画、视频或图形渲染的流畅度。数值越高，画面越流畅。
