我从0到1主导了基于webgl的渲染器引擎的整体重构，将帧率从 5fps 提升至稳定 55fps+，支撑 10w+ 地理点位的实时渲染。

问题根源是原有方案用 DOM Marker 渲染每个点位，数据量超过 1000 个时，浏览器频繁触发 Layout 和 Repaint，帧率直接崩到 5fps 以下，必须从架构层面换掉。

我把它拆成三层解决：第一层是渲染架构，引入 LOD 调度——远景用 GeoJSON cluster 图层交给 GPU 一次性渲染，近景保留 Marker，帧率立刻从 5fps 回到 55fps+；第二层是增量更新，利用 Mapbox GeoJSON Source 的 diff 机制，给每个 Feature 挂稳定 id，从全量替换改为只上传变化部分，刷新卡顿从 800ms 降到 20ms；第三层是线程分工，把格式转换、去重、坐标过滤拆到 Web Worker，主线程不再感知数据处理，页面交互始终流畅。

---

渲染问题解决后，我们要在平台上加 AI 灾害分析。直接调 OpenAI API 很快发现不够用——实际场景需要"先检索历史灾害、再让 LLM 研判、最后按严重程度走不同预警分支"，这种多步骤有条件判断的流程，一次 API 调用根本描述不了。而且这不只是这一个项目的问题，公司各业务线都在重复实现同样的 LLM 调用逻辑，复用性极差。

所以我主导从零设计了一套 AI 工作流执行引擎，核心难点有三个：一是用注册表模式统一调度异构节点，节点间通过 `{{nodeId.output}}` 变量插值传递数据，引擎只管按拓扑顺序执行；二是 LangGraph 多分支场景下状态容易污染，通过严格定义状态结构和边条件函数来约束，保证对话历史始终完整；三是本地 Ollama 模型和云端 OpenAI 接口不兼容，加了一层模型适配器，切换模型只改配置不改业务逻辑。

这套引擎最终以 SaaS API 对内开放，集成进了 Prometheus 的 AI 分析模块，API 成功率 99%+，首字响应低于 1 秒。
